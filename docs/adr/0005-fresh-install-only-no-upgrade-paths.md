# ADR 0005：数据库与备份契约只服务全新安装（版本重置为 1，无升级路径）

日期：2026-09-01
状态：已接受

## 背景

App 未上线、没有真实用户数据，但历史上积累了两套升级兼容设施：

- 数据库 `schemaVersion` 已到 9，`onUpgrade` 里有 v1→v9 共 8 段升级代码
  （重建表、加列、删列、挪列、补索引），配套两个迁移测试和专用的
  `withExecutor` 临时文件库构造器；
- 备份 JSON `schemaVersion` 已到 4，解码同时接受 v2/v3/v4，含"老备份缺
  动力类型字段按燃油恢复"之类的回退分支，配套 5 处兼容测试；
- 车型目录 asset 自带 `schemaVersion: 2`（防旧格式数据灌入的加载校验）。

这些代码只服务于"开发机上的旧库还能继续用"，而开发数据本可随时丢弃。
维护它们需要每改一次表结构就写一段升级分支，与"简单干净的系统"目标相反。

## 决定

1. **版本号全部重置为 1**：数据库 `schemaVersion = 1`、备份 JSON
   `schemaVersion = 1`、车型目录 asset `schemaVersion = 1`。三者仍是
   相互独立的版本号，只是起点归一。
2. **数据库删除全部升级路径**：`migration` 直接返回 Drift 的
   `destructiveFallback`——打开库时版本与代码不一致（无论升还是降），
   就把全部表按倒序删掉再重建。效果：开发期改表结构只要版本号 +1，
   旧开发库在下次启动时自动清空重建，不再手写任何升级分支。
3. **备份解码只认 v1**：版本号不是 1 直接拒绝； cars 条目的
   `powertrainType` 为必填字段，不再有"缺字段按燃油恢复"的回退。
4. **车型目录加载校验保留**（`schemaVersion != 1` 即报错），这是防
   旧格式目录数据灌入的读取校验，不属于升级兼容。
5. **上线前的改表纪律**：改 Drift 表结构必须把 `schemaVersion` +1
   （+1 本身就是触发删库重建的开关），不允许改表不加版本号。
6. **正式上线后本决定作废**：有真实用户数据时，升级路径重新变为必须，
   届时另立 ADR 恢复"版本号 +1 并补升级分支"的纪律。
7. **配套清理**：删除迁移/备份兼容相关测试（迁移测试、v2/v3 备份测试、
   `withExecutor` 构造器）；删除过期迁移/修复文档（batch-migration-plan、
   migration-implementation-report、review-fix-todo、code-review-fix-plan、
   car-catalog-model-name-duplicates、docs/prototypes/）；
   `current-database-schema.md` 重写为纯"当前结构"描述；
   `code-review-report.md` 瘦身为仅未修条目（编号不重排）。
   保留项（产品决策，不在本清理范围）：思域专属模板旁路（ADR 0004）、
   示例油价数据源（ADR 0001）、开发者模式、各表
   syncStatus/updatedAt/version 云同步预留列。

## 后果

- 代码里不再有任何"老数据怎么变成新结构"的逻辑；系统只有一条路径：
  全新安装 → `createAll` 建库 → bootstrap 灌目录。
- 开发机上的旧 v9 库首次打开会被自动删库重建，无需手动卸载；
  之前导出的 v4 备份文件导入会被拒（重新导出即可）。
- 以后读代码不需要解释"为什么数据库版本已经 9 了"，三个契约版本
  与产品 v1 说法一致。
