# ADR 0012：停车倒计时 iOS 实时活动走原生 ActivityKit + Widget Extension 桥接

日期：2026-09-15
状态：已接受

## 背景

停车倒计时的系统外呈现目前是"Android 常驻 chronometer 通知（id 9002）+ 到点/预警通知（9001/9003/9004）"，iOS 只拿到三张预定通知，没有任何常驻实时展示——iOS 本地通知无"常驻"能力。用户需求：倒计时进行中在通知里常驻、实时可见，并支持灵动岛。iOS 对应的系统能力是实时活动（Live Activity，iOS 16.1+）：一套实现同时覆盖锁屏卡片、灵动岛、通知中心顶部区域，由系统托管自动走秒、App 无需保活。仓库现状是张白纸：无 Widget Extension 目标、无相关插件、部署目标 13.0，git 全史（含悬空提交与 feature 分支）无任何实时活动代码——先前在仓外验证过的一版不迁移复用，按本仓现状新写。

## 决定

1. iOS 用实时活动承载停车倒计时的常驻展示；Android 维持现有 ongoing chronometer 通知，**零改动**。
2. **原生实现，不引第三方插件**：新增 Widget Extension target（只写停车倒计时一种 ActivityAttributes）；Dart 侧新增 `lib/core/platform/native_live_activities.dart` 纯通道桥接（模式学 `native_notification_settings`，可注入假实现做单测）；Swift 侧通道代码住 SceneDelegate.swift（跟随现有 scene 生命周期接线惯例）。
3. **零更新渲染**：卡片内容全部用系统自动走时组件——`Text(timerInterval:)` 倒计时数字、`ProgressView(timerInterval:)` 进度条，App 全程不推送任何更新、不保活，样式在启动活动时一次算定。临期警示继续走既有预警通知（9003/9004），卡片不变色、不换文案。
4. 卡片内容（用户决策 2026-09-15）：**剩余时间数 + 进度条**（走满 100% 即到点时刻）；不放开始/结束钟点，不放车辆名——倒计时是全局临时偏好、不挂车，放车名会制造"倒计时属于这辆车"的错误暗示。灵动岛收拢态只有图标 + 倒计时，进度条只在展开态与锁屏卡片。
5. 到点收场（用户决策 2026-09-15）：对齐 App 内"到期不自动清除、红字正计时等手动结束"（R9）——活动不撤，`staleDate = endsAt` 让系统自动置灰为已到期样式；**App 下一次运行时**（点开到点通知、回前台、冷启动）由对账逻辑把它切成正计时模式（"已超时"，系统自动正跳，此后仍零更新）；用户在 App 内点"结束"才真正撤卡。到点 alarm 与预警通知职责不变。已知成本：App 不在跑到点的那段窗口里，卡片停在 00:00 + 置灰，不会自动开始正计时——ActivityKit 的更新只能由运行中的 App 或服务器推送发起，本地无定时更新手段，这是接受的折衷。
6. **生命周期归属**：启停编排挂进通知协调器（LunioNotificationCoordinator），不建第二个协调器。清单：保存 → 启动/重建；App 内清除/改目标 → 撤/重建；清空数据 → 撤；**删车、恢复备份 → 不动**（与停车通知现状一致：倒计时全局不挂车、备份不含倒计时偏好）；通知总开关 → 不跟随（实时活动在系统设置里是独立开关）；用户在系统级关闭实时活动 → 创建/更新抛错静默吞掉，降级为"只有通知"。对账三态（冷启/回前台执行）：偏好有倒计时 + 系统无活动 → 补启（覆盖手机重启丢活动、系统寿命上限收回）；偏好无 + 系统有 → 撤；两者都有但形态过期（到点后未切正计时）→ 原地更新。
7. 部署目标保持 13.0 不抬：桥接与 Extension 代码用 `@available(iOS 16.1, *)` 运行时守卫，低版本/关闭实时活动的设备行为与现状完全一致。已知系统上限：实时活动有约 8~12 小时寿命，超长倒计时的活动会被系统收回，卡片消失但到点/预警通知不受影响。

## 后果

- iOS 工程首次引入第二个 target（Widget Extension）：签名、构建配置、依赖接线都要维护，构建时间略增。本机模拟器构建当前不可用（运行时/SDK 错配，见 2026-09-12 记录），灵动岛观感只能真机验收。
- 零更新方案换来系统侧绝对稳定（不会被系统冻结/限流，杀 App 照走秒），代价是"到点切正计时"存在回 App 前的窗口期（决定 5）。
- 实时活动不是通知，但编排挂在通知协调器：接受这个职责上的轻微越界，换取停车倒计时"系统外呈现"的单一拥有者，通知清扫模板旁一处扩展、避免两处对账打架。
- 两平台展示不完全对齐：Android 通知正文有"免费离场时间 HH:mm"钟点，iOS 卡片不放钟点——Android 零改动是本轮拍板，各自贴合平台习惯，不强行统一。

## 备选方案

- **第三方插件**（live_activities 等）：接入快，但锁死 ActivityAttributes 形态与升级节奏，且仓库约定不随意引新框架；原生面很小（一种活动、启/更/撤三四个方法），自己握着更稳。
- **只做锁屏卡片、不做灵动岛**：灵动岛本来就是实时活动的呈现之一，没有独立开关，拆分无意义。
- **到点即撤活动**：与 App 内"到期不自动清除等手动结束"（R9）不一致，用户可能还没看到就没了。
- **中途变档**（剩余 30 分钟卡片变警示色）：iOS 无可靠的定时后台手段，中途改样式只能靠不可靠的后台任务或服务器推送；维持零更新，警示职责留给预警通知。

## 修订

- **2026-09-15 实施修订**：系统守卫与扩展部署目标从 16.1 提到 **16.2**——到点置灰依赖的 `ActivityContent(staleDate:)` 与 `end(_:dismissalPolicy:)` 都是 16.2 API。Widget Extension target `ParkingCountdownExtension` 部署目标定 16.2，Runner 侧通道执行体（`ParkingCountdownActivityController`）用 `#available(iOS 16.2, *)` 守卫；16.1~16.2 之间未升级的极早期设备按"低版本"降级为只有通知。Attributes 共享文件（`ParkingCountdownAttributes.swift`）以显式文件引用同时编进 Runner 与扩展两个 target。
- **2026-09-15 二轮（真机验收反馈）**：① 决定 3 的"卡片不变色"修订为**档位色两事件算定**——启动/补启时按 App 内 ParkingCountdownRules 同一规则算定色档（剩余 >20% 绿 / ≤20% 黄，随 ContentState.colorKind 传入），到点对账切正计时这一次 update 强制红色；仍零推送（两次样式都伴随既有事件，不存在定时推送）。② 到点正计时口径对齐：从"到点时刻起算超时时长"改为**从入场时刻起算总"停车时长"**，与 App 内到期卡片数值一致（真机反馈两侧不一致）。③ 结束撤卡确定性：`stop` 改为原生侧确认全部 `end` 完成后才回包——fire-and-forget 在 App 随即退后台时可能没执行完，残卡要等下次对账才撤。④ 视觉升级：紧凑态主题色圆徽标 + 数字着色，展开态进度条加粗着色，锁屏卡主题色底白字（色值按 DESIGN.md LunioTokens success/warning/danger 同步为常量副本）。⑤ "开始/结束不及时上岛/撤卡"现象定性为**模拟器 WidgetKit 渲染调度不实时**（活动事件滞后到下一次前后台切换才反映），真机为即时——待真机复验。
- **2026-09-15 三轮（样式定稿 + 到点感知）**：做了 A/B/C 三套结构迥异的 PROTOTYPE 变体（每保存一次轮换）供真机验收，用户拍板 **A 行式对照**（借鉴 live_island 插件示例的布局语言：青色图标 + 金黄计时 + 灰色状态行 + 蓝色进度条 + 黑底锁屏），B/C 与轮换逻辑已删除。定稿调整：① 决定 3 的"档位色"在此样式中弃用（固定 live_island 配色），colorKind 通道删除；② 展开态重排——不设 leading 区（岛左圆角裁掉贴边图标）、时间居中、状态右上、进度条左右留圆角安全边距；③ 进度条改**剩余递减**（countsDown，到点走空 0%），文案改"免费停车还剩 / 免费停车已结束，请尽快离场"；④ **到点感知**：App 在前台时由停车卡片的秒时钟跨越到点的那一刻经动作层调 `markParkingLiveActivityExpired` 即时切"已超时"（红色状态），App 不在前台仍无法本地定时（系统不唤醒），由回前台/冷启动对账兜底。
- **2026-09-16 四轮（居中与截断）**：展开态与锁屏统一为同一主行（MainRow）：最左 P 图标 + 文案，计时居中，最右状态。两个系统级坑及对策：① 计时 Text 是贪婪布局且按最大可能表示预留宽框、数字靠左画在框内——HStack（含定宽框居中）里时间永远偏左、还会挤压文案截断（定宽框方案实测失败），改为**三层 ZStack**：时间层独占整行、靠 `multilineTextAlignment(.center)` 让系统把数字画在行中心，文案/状态两层贴边浮在两侧互不挤压；② 到点态文案缩短为"请尽快离场"（原"免费停车已结束，请尽快离场"在岛内被截断）。锁屏卡同步放大（计时 .title 加粗、两侧 .subheadline、内边距 16）。主行文案最终由用户定稿（2026-09-16）：进行中"**免费时长**"、到点"**已停时长**"（与 App 内"停车时长"正计时口径呼应）。
- **2026-09-16 五轮（真机调试 + 后台保活卫生）**：`ParkingCountdownActivityController` 的 start/stopAll/markExpired 一律经 `runKeptAlive` 包进 `beginBackgroundTask` 后台保活执行（completion 与 expiration 双路收场、恰好回包一次，到期按"未完成"静默降级回 false）——ActivityKit 的 request/end 同步返回 ≠ 与系统守护进程的异步握手完成，退后台随即挂起会让握手半路夭折。保活只对"已经在跑"的工作有效、不能定时唤醒，**后台到点翻转维持决定 5**（回前台对账兜底；本地通知 9001 到点照发，样式翻转等回 App），服务器 push 仍暂不做。
- **2026-09-16 六轮（真机日志实锤误撤根因，主修复）**：真机 attach 日志证明"开始后没上岛"的主凶**不在原生层**，而在 Dart 对账：保存链 `invalidate(parkingCountdownProvider)` 触发对账监听，invalidate 后 provider 重建完成前仍暴露旧值（Riverpod 3 语义），对账读到"无倒计时"的旧快照 → 按"偏好无 + 活动在 → 撤"把刚启动的活动停掉（日志实锤 start 后 18ms 被 stop；跨后台挂起的"僵尸对账"回前台完成后同样误杀）。修复：`reconcileParkingLiveActivity()` 不再收 provider 快照参数，**对账时直读偏好表拿当下真值**，与 provider 重建时序天然解耦；三态判定逻辑不变。协调器对账 8 用例改为偏好门面播种，371 测试全绿。
