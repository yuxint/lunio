# ADR 0014：加油记录——流水表、满箱段油耗口径、不联动车辆里程

日期：2026-09-17
状态：已接受

## 背景

加油域此前只有油价预测（预估加满花多少钱），没有加油流水；真实百公里
油耗和每公里油费算不出来，油价预测缺一个"我自己加一箱要花多少"的落地
闭环。产品拍板：加油页新增"加油记录"卡，五项字段（日期/里程/金额/升数/
是否加满）30 秒记一笔，单价自动算只读，满箱段口径计算油耗。

关键取舍：

1. **要不要 {carId, date} 唯一约束**：保养记录"一天一条"成立是因为
   保养是低频事件；加油是高频事件，长途一天两箱是常态而非脏数据。
   唯一约束会把合法数据挡在库外，因此加油记录**故意不设**唯一约束，
   也不做"同日查重"业务校验（与保养记录 R4 的口径刻意相反）。
2. **加油记录要不要联动车辆当前里程**：保养记录保存时会用
   max(当前值, 记录里程) 抬升车辆里程（只增不减）。如果加油记录也这么
   做，两个写源会竞争"谁的里程更新"——加油通常晚于保养发生，看似加油
   抬升更合理，但补录保养记录（日期早、里程高）时又会反向矛盾。拍板：
   **保养记录是车辆里程的唯一写源**，加油记录的里程只是流水快照，不
   回写 `cars.currentMileageKm`（spec 用户故事 36）。
3. **单价要不要落列**：单价 = 金额 ÷ 升数，随时可算；落列反而引入
   "手填单价与金额/升数矛盾"的一致性问题。五项精简录入（无加油站/
   备注字段），单价不落表、展示层现算。
4. **升数的精度**：与油箱容积（`cars.tankCapacityLiters`，real）同
   先例，用 double 存升；金额仍用"分"（int），与保养记录同口径。

## 决定

1. **数据模型**：新表 `fuel_records`——id（雪花）、carId、
   date（text yyyy-MM-dd）、mileageKm（int 公里）、volumeLiters（real
   升）、totalCostCents（int 分）、fullTank（bool）+ sync 三列
   （syncStatus/updatedAt/version，全库约定）。无唯一约束；carId 普通
   索引 `idx_fuel_records_car_id`（按车拉流水，与保养记录同先例）。
   数据库 `schemaVersion` 2→3（ADR 0005：版本不符删库重建，无升级分支）。
2. **校验**（实体构造即校验 + 仓库写库前统一校验，与 FuelPrediction
   同先例）：里程 ≥ 0、金额 ≥ 0、升数 > 0（0 升的"加油"没有物理意义）。
   日期范围同保养记录（上路日期起、允许未来），属表单层规则（随加油页
   UI 票落地）。
3. **满箱段油耗口径（full-to-full）**：
   - 记录按（日期、里程、id）升序——这也是仓库列表查询的固定排序；
   - 一条记录"闭合一段"当且仅当**它加满**且**存在更早的满箱记录**
     （锚点）；首条满箱只做锚点不闭合段；
   - 段升数 = 锚点之后至闭合条（含）的升数之和——部分加油（非满箱）
     的升数计入所在段；
   - 段里程 = 闭合条里程 − 锚点里程，≤ 0 视为该段无效（折叠，不计入
     均值），保证乱序/同日数据不出负数油耗；
   - 平均油耗 = 有效段升数和 ÷ 有效段里程和 × 100（L/100km）；每公里
     油费用各段金额同理计算；
   - 无有效段（不足两条满箱、或全部段里程非正）时不显示摘要。
   - 口径实现为领域纯函数（FuelRules），随加油页 UI 票落地并有单测 +
     变异验证。
4. **失效与动作层**：按车 family provider
   （`fuelRecordsForCarProvider`）+ 当前应用车派生 provider
   （`appliedCarFuelRecordsProvider`，仿加油预测派生模式）；family 并入
   `invalidateVehicleProviders` 整族失效名单；动作层新增
   saveFuelRecord / removeFuelRecord 两函数（写库 → 失效，ADR 0007），
   确认框留调用方。
5. **删车级联**：复用主仓库借道加油仓库的既有接缝——
   `FuelRepository.deleteForCar` 扩展为同时删预测行与加油记录，主仓库
   `deleteCar` 事务零改动。
6. **备份（备份 v3 票已实施）**：备份 JSON `schemaVersion` 2→3，接受
   版本 [1, 2, 3]；加油记录作为新数组字段 `fuelRecords` 导出/导入
   （条目不带 id，恢复时重新生成雪花，与 `fuelPredictions` 同先例），
   v1/v2 文件缺字段按"无加油记录"读入（纯增量缺失，沿用 ADR 0010
   先例）；恢复事务内 carId 重映射 + 引用完整性校验 + 业务规则校验 +
   恢复清表名单加新表；油价缓存/手填油价仍不进备份。数据层票已先行
   把清空数据名单覆盖新表。

## 后果

- 数据库 schemaVersion 3：旧开发库下次启动自动删库重建（ADR 0005），
  不是事故。
- 加油记录不进"同日查重"、不联动车辆里程——依赖"一天一条""里程随
  记录抬升"直觉写的新代码要小心，这两条规则只属于保养记录。
- 油耗数字只在满箱段口径下成立：部分加油只贡献升数，不闭合区间；用户
  长期不加满时看不到油耗摘要，属预期行为而非缺陷。
- 备份 v3 已随备份票落地，数据层先行留下的过渡窗口（清空数据删了
  加油流水但导出不含它、恢复清表不含新表会留孤儿行）已关闭：导出/恢复
  均含加油记录，恢复前残留的加油记录随清表一并清除。
