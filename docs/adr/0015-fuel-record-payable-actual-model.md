# ADR 0015：加油记录模型重定义——应付/实付五字段、容积预留、v3 就地重定义

日期：2026-09-22
状态：已接受（部分取代 ADR 0014 的记录模型与满箱段油耗口径）

## 背景

加油记录的第一版（ADR 0014，五字段：日期/里程/金额/升数/是否加满）
随加油页第三卡上线三天后即被屏蔽（2026-09-20，commit 005eaa2："功能
是雏形，细节待打磨，先不对用户可见"）。用户复盘后的核心不满：记一笔
要填的与用户真正关心的不对齐——用户只关心"哪天、什么油、多少钱"，里程
/升数/加满都是负担；满箱段油耗口径依赖里程与加满两个输入，用户不要
求记账时提供它们。

产品拍板重新设计（grill 三轮定稿）：

1. 记一笔只填五项：**日期、油品（默认 92#）、单价、应付金额、实付金额**
   （后两者是两笔钱：应付 = 加油机口径 = 单价 × 容积；实付 = 优惠后
   实际支付）。这与保养记录"项目费用合计 vs 总费用（优惠）"的软提示
   模型同构，但更简单：实付选填，没填 = 无优惠，不设"不一致"提示。
2. **容积反推预留**：容积 = 应付 ÷ 单价，实体构造时算好落库，但页面
   暂不展示——为将来油耗等功能留数据，与 `cars.tankCapacityLiters`
   油箱容积（车的属性、加满预估用）无关。
3. 终点是**费用统计**：统计页新增独立"加油费用"卡（按年 + 按月），
   保养各卡口径零改动；记录页头部汇总行改"今年保养 + 今年加油"。

关键取舍：

- **应付/实付两笔钱 vs 一笔钱**：两笔钱对应加油站优惠的真实场景
  （泵显 300、实付 270），统计按实付才是真花钱；合一会丢优惠信息。
- **单价落列 vs 不落列**：ADR 0014 拍板"单价不落列"是因为单价可由
  金额÷升数推出；新模型里单价是**用户输入**，应付也是用户输入，容积
  才是派生值——权威值与派生值身份互换（沿 ADR 0010 的"用户输入 =
  权威值、派生值不落库/落库不信任"哲学）。
- **版本号就地重定义（本 ADR 最不寻常的决定）**：按 ADR 0005 修订版
  政策，改表结构必须 `schemaVersion` +1。但 v3 的加油功能从未真实
  使用（入口屏蔽期间无数据、无含加油条目的真实备份），把"从未兑现的
  v3"空号跳过会让版本历史失真。拍板：**DB 与备份都保持 v3，表结构
  就地重定义**，代价是——
  - 旧 v3 库（含旧 `fuel_records` 表）对新代码不再兼容，**必须卸载
    重装**，不提供原地升级；
  - 含旧结构加油条目的 v3 备份文件解码失败、整单被拒（拍板接受：
    不存在这样的真实文件）。
  曾评估过"先升 v4 → 重装导出 → 降回 3 → 恢复"的过渡流程，因"v4
  备份在降级后不可恢复"的缺陷与多一程安装成本被否。
- **删除满箱段油耗**：里程/加满两输入被删，full-to-full 口径失去
  输入。`FuelRules` 的段划分/平均油耗/每公里油费函数、卡上摘要与行内
  油耗 UI 一并删除；ADR 0014 的记录模型部分由本 ADR 取代（无唯一
  约束、不联动里程两条保留，只属于加油记录的直觉不变）。
- **日期上限收 today**：保养与加油记录日期均改为不能选未来
  （原"允许未来"作废）；两域共用规则。
- **油价卡/预估卡/加油 tab/开发者开关全部保留**：本轮只动记录卡，
  油价域（ADR 0006/0011）原样；顺手收益：记一笔的单价在表单油品 =
  油价卡油品时预填生效价（可改，只在开表单时生效一次）。

## 决定

1. **数据模型**：`fuel_records` 表就地重定义（DB `schemaVersion`
   保持 3）——id（雪花）、carId、date（text yyyy-MM-dd）、grade
   （text，FuelGrade 稳定 code）、unitPriceCents（int 分/升）、
   payableCents（int 分）、actualCents（int 分，**可空**）、
   volumeLiters（real 升，两位小数）+ sync 三列。删除
   `mileage_km`/`full_tank`。无唯一约束与 carId 索引沿用。
2. **校验**（实体构造即校验 + 仓库写库前校验）：单价 > 0、应付 > 0、
   实付可空但填了必须 ≥ 0（实付 > 应付合法，不拦截——用户自己的账）。
   日期范围：上路日期起、**上限今天**（表单层规则，与保养记录一致）。
3. **容积唯一算法**：`FuelRecord` 构造时算 `应付 ÷ 单价`（四舍五入
   两位小数），不接受外部传入；备份恢复时同样重算、不读备份存值。
   备份条目仍导出 `volumeLiters`（镜像库内预留列）。
4. **备份**：备份 JSON `schemaVersion` 保持 3，接受版本 [1, 2, 3]
   不变；v3 的 `fuelRecords` 条目结构以本 ADR 为准（carId、date、
   grade、unitPriceCents、payableCents、actualCents、volumeLiters、
   sync）。含旧结构条目的 v3 文件解码失败即拒绝恢复。
5. **加油费用口径**：一笔加油参与统计的钱 = 实付金额，没填取应付
   （`FuelRecord.effectiveCostCents` 唯一实现点）。聚合纯函数在
   `fuel_cost_stats.dart`（年度行从首条记录年铺到今年补 0、最近年
   在前；月度 12 桶），统计页"加油费用"卡 = 总费用/笔数 + 年度行
   （点行切换）+ 选中年 12 个月条形（同日二轮反馈：卡片**固定页面
   最后**、头部金额标签用"总费用"）。保养汇总卡在有加油记录时追加
   "今年加油"第三栏（总费用｜今年保养｜今年加油；无加油记录不显示
   该栏），保养各卡（守恒、优惠分摊、月均）不含加油、"总费用"仍为
   保养口径（占比卡守恒锚点不动）。统计页空态守卫放宽为"保养 +
   加油都无记录"；只有加油时保养区降为一行轻提示。记录页头部汇总行
   = "今年保养 ¥x + 今年加油 ¥y"，任一非空即显示、两段按域各自显隐
   （无加油记录不显示"今年加油"，反之亦然）。走势卡改名"保养费用
   走势"。
6. **升级与恢复操作口径（用户手工流程）**：当前版本导出备份 → 卸载
   重装新包（全新 v3 库建出新结构）→ 恢复备份。备份不含偏好（主题等
   需重设），`appliedCarId` 指向恢复出的第一辆车（既有口径）。

## 后果

- `fuel_records` 的两个历史形态共用"v3"版本号——靠本 ADR 与
  `docs/migration/current-database-schema.md` 的例外标注说明；
  未来任何再改 `fuel_records` 必须真正 +1 到 v4，不得再次就地
  重定义。
- 旧 v3 库对新代码会因缺列崩溃（no such column），这是拍板接受的
  风险，缓解手段是卸载重装；测试与文档不得假设旧 v3 库可升级。
- 满箱段油耗与"每公里油费"从此无数据来源；CONTEXT.md 对应词条已标
  删除。若未来恢复油耗功能，应基于预留的 `volume_liters` 列重新
  设计口径并出新 ADR。
- 加油费用与保养费用在统计页保持两套互不掺和的口径；"总养车费用 =
  保养 + 加油"的合并汇总是后续可选项，本轮不做。
