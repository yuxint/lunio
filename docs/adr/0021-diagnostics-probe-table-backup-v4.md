# ADR 0021：车辆诊断数据模型——全局检测点表、bootstrap 种子与备份 v4

日期：2026-11-12
状态：已接受

## 背景

车辆诊断的页面数据条目是「检测点」（GLOSSARY 词条）= 一条指令 +
一种解析方式 + 一个展示位，用户可自定义。需要拍板指令库挂在什么
维度、种子怎么来、进不进备份。ELM327 标准 Mode 01 指令语义与具体
车辆无关（`012F` 在任何支持的车上都是油量液位百分比），本功能当前
单车自用，但指令库没有理由绑在车辆维度上。

## 关键取舍

- **全局表 vs 每车一套**：指令语义与车无关，全局一份；车辆维度的
  个性数据（油箱容积）已有 `cars.tankCapacityLiters` 承载（升数
  估算用）。每车一套是为"不同车用不同指令"的场景付复杂度，该场景
  不存在。
- **进备份 vs 当临时数据**：自定义检测点是用户的劳动成果，性质同
  保养项目不是油价缓存——进备份。新增段是纯增量：按 ADR 0005 政策
  DB `schemaVersion` 3→4（`if (from < 4)` 建新表，存量数据保留），
  备份 JSON 同步升 v4、兼容读 v1–v3（缺段=空）。
- **解析能力用类型枚举，不做公式表达式**：油量百分比 / 温度
  （A−40）/ 电压文本 / 原始 hex 兜底，四种覆盖内置种子与常见标准
  PID；自由公式引擎是 v2，避免 v1 背上 DSL 安全与校验负担。

## 决定

1. 新增全局表（暂名 `diagnostics_probes`）：雪花 id、名称、指令
   原文、解析类型（枚举）、启停、内置标识（稳定 catalogKey，供
   bootstrap 对账）+ sync 三列；不挂 carId。列名与类型在 spec
   定稿。
2. DB `schemaVersion` 3→4，onUpgrade 增量 `if (from < 4)` 建新表；
   沿 ADR 0005（增量迁移政策修订版）。
3. 内置三条种子（油量 `012F`、水温 `0105`、电压 `ATRV`）由
   bootstrap 幂等对账写入，入口并入 `ensureBootstrapData()`；对账
   只作用于内置标识集合，不碰自定义行。**内置项只读**（名称/指令/
   解析类型不可改、不可删，可启停），自定义项才可增改删——对账
   语义因此保持目录式安全："内置行永远等于内置值"。
4. 备份 JSON `schemaVersion` 3→4，白名单 [1,2,3,4]；新增
   `diagnosticsProbes` 段，decode 缺段=空（沿 `fuelRecords` v3 先
   例）；恢复事务内重插该段，条目不带 id、恢复时重新生成雪花 id
   （沿 fuelRecords 条目先例，无外键重映射负担）。**段只导自定义
   项**，内置不进备份、恢复后由 bootstrap 重建（对齐车型目录先例）。
5. 解析类型枚举四种：油量百分比 / 温度（A−40）/ 电压文本 / 原始
   hex。

## 后果

- 备份升版单向：新版本读 v1–v4，老版本读 v4 会被白名单拒绝，沿
  既有口径不回写兼容。
- 检测点表不挂 carId，删车不级联、与车辆数据纪元无关（该表写点
  不 bump 车辆纪元，不进通知同步数据源清单）。
- 内置检测点被改坏的风险在对账语义下不存在；用户想换指令走新增
  自定义项，内置三件套是"永远正确的兜底"。

## 修订节（2026-11-15，最后读数持久化）

- **需求**：读数原先只在页内内存，离页即丢、重进显"—/未更新"。拍板
  持久化「最后读数」（GLOSSARY 词条）= 检测点最后一次**有效**轮询的
  展示值与时刻，重进页面可见。
- **数据形状**：`diagnostics_probes` 加三列——`last_value`（展示值
  文本，可空）、`last_percent`（油量百分比 real，可空；油量卡升数
  估算重进后不缺数据）、`last_reading_at`（ISO 8601 文本，可空）。
  DB `schemaVersion` 4→5 增量 ADD COLUMN，存量保留（升级后列值
  NULL = 还没有最后读数）。迁移纪律：`createTable` 永远建当前形态
  的表，建表分支与加列分支必须互斥（else-if），否则跨版本老库先建
  出含新列的表再加同名列会 duplicate column；v6 起沿用。
- **只存有效值**：「无数据」读数不写库、不覆盖旧值；页内实时显示不
  受影响（无数据照显灰字）。有意接受的后果：会话中显「无数据」时，
  重进页面会显上次有效读数（读数带时刻，语义是"最后有效值"而非
  "当前值"）。
- **写库时机**：页面每收到一个有效读数写一次（轮询节奏，约每秒 1
  次）。`saveProbeReading` 只 UPDATE 读数三列，`syncStatus` /
  `updatedAt` / `version` 有意不动——读数写点与表单/启停写点分叉，
  高频写不盖同步章。（如果盖章，每秒都会把同步元数据翻成待同步，
  同步语义失去意义；读数是设备派生临时数据，不是用户数据。）
- **备份不携带**：导出 payload 显式剥掉读数三列，备份 JSON 条目本就
  无这些字段；恢复后从零积累。删检测点列随行删，无需单独清理。
- **时间格式**：`formatReadingTime`（`core/format/clock.dart` 纯函
  数）——今天显 `HH:mm:ss`，非今天显 `M/d HH:mm:ss`（跨天读数带日
  期，避免只显时分秒误导）；now 由调用方注入，可单测。
- **油量、水温核心值卡同源恢复**：行列表与核心值卡共用同一快照取
  值（`_snapshotFor`：实时读数优先，无实时时回退持久化读数）。

## 修订节（2026-11-15，每车检测点、内置可编辑与备份 v5）

- **背景与推翻的旧决定**：原决定 1/3 的"全局表、内置只读"在实车
  验证后不再成立。用户要求检测点管理与保养项目看齐；不同车辆可能
  使用不同指令（本田私有 DID 只对思域有效），且水温标准 PID 05
  在本车不被支持，需要能通过 UI 改成私有命令。因此检测点改为
  **每车一套**，内置三条**可编辑但不可删除**。
- **数据形状**：`diagnostics_probes` 加 `car_id`（存储可空、代码层
  必填；迁移时存量行归第一辆车）、`refresh_interval_seconds`
  （INTEGER NOT NULL DEFAULT 30）、`header`（TEXT 可空，私有 DID
  预留，本轮无 UI）。唯一键由 `{catalogKey}` 改为
  `{carId, catalogKey}`；SQLite 不能 ALTER 唯一约束，需要重建表。
  `cars` 加 `total_tank_capacity_liters`（REAL 可空，双油量见
  ADR 0022）。
- **内置种子**：每辆车三条（油量 `012F`、水温 `0105`、电压
  `ATRV`），默认刷新间隔 30 秒。新增车辆时播种；bootstrap 按车补
  缺失内置。**只补缺失、不纠偏用户编辑**——内置行可改名称/指令/
  解析类型/间隔/启停，不可删；自定义检测点照旧可增改删。
- **核心值卡**：油量/水温卡按 `catalogKey` 在**当前应用车辆**的
  检测点里定位；内置行编辑后卡片继续消费同一条；自定义检测点不
  影响核心卡。
- **刷新规则**：每个检测点独立间隔，默认 30 秒，范围 5–3600 秒；
  轮询按各条到期时间调度；手动刷新立即轮询全部启用项；调试终端打
  开时暂停自动轮询（ADR 0023）。
- **删车级联**：删除车辆时在同一事务内删除该车检测点；检测点不进
  入车辆数据纪元（写点仍走 provider 点失效）。
- **备份 v5**：`diagnosticsProbes` 条目加 `carId`、
  `refreshIntervalSeconds`、`header`；仍只导自定义项，内置由每车
  bootstrap 重建。`cars` 条目加 `totalTankCapacityLiters`。解码接
  受 v1–v5；v1–v4 的全局检测点恢复到第一辆车，缺省间隔 30、缺省
  header/总容积 null。
- **迁移链清理**：v5→v6 沿用"建表分支永远建当前形态、建表与加列
  互斥"的纪律，并把现有重复的 `from < 4` 建表分支收敛成单链；补
  v2/v3/v4/v5→v6 迁移测试。
- **私有 DID**：本轮只做调试/验证，不进正常轮询；验证通过后再用
  `header` + 多帧重组 + 私有解析类型替换内置水温或新增实测油量检
  测点（ADR 0023）。
