### 1. 备份恢复放行负里程车辆

- 位置：`lib/data/repositories/backup_repository.dart:497`
- 症状：恢复一份把车辆 `currentMileageKm` 改成负数的备份会成功落库；提醒进度、
  车辆卡片里程和记录里程软提示随后按负值计算/展示。
- 错误依据：手工录入的里程门禁在 `lib/features/shell/profile/car_form_controller.dart:193`
  （`reportError('当前里程必须是非负整数')`）；`Car` 实体没有 validate；备份业务
  规则注释承诺「与手工录入走同一套规则，篡改过的备份（负金额/负里程/空项目/
  非法间隔）在开事务前就被拒绝」。
- 证据级别：已复现（数据层用例先红后绿）。
- 触发路径：裸插一辆 `currentMileageKm: -5` 的车（绕过表单/仓库校验，模拟被
  篡改或损坏的备份来源）→ 导出 payload → `restoreBackupPayload` → 车辆循环只
  校两个容积 → 事务清库重插，负里程进库。
- 复现：`flutter test test/data/backup_restore_test.dart --plain-name 'negative car mileage'`
  — 修复前 `Expected: throws <LunioErrorException...> / Actual: returned a Future
  that emitted <null>`（恢复成功）；修复后通过。
- 根因：`_validateBackupBusinessRules` 的车辆循环漏了里程非负检查。
- 修复：车辆循环补 `if (car.currentMileageKm < 0) throw ArgumentError('当前里程
  不能为负数')`，沿用该循环的 `try/on ArgumentError → LunioErrorException
  (backupInvalidData)` 包装；catch 文案从「油箱容积」放宽为「车辆」以覆盖两类
  错误。
- 回归：`flutter test test/data/backup_restore_test.dart` 21 用例全部通过。
- 提交：96dccfc

### 2. 备份恢复允许无启用项目的车辆

- 位置：`lib/data/repositories/backup_repository.dart:533`
- 症状：恢复一份车辆存在、但没有任何启用保养项目的备份会成功；恢复后该车在
  记录表单里没有可选项目（无法新建保养记录）、提醒页进入「无启用项目」空态，
  且现有写入口不会自动补项目。
- 错误依据：手工建车 `createCarWithMaintenanceItems`（`lunio_repository.dart:69`）
  要求至少一个启用项目；停用/删除项目都走 `_ensureCanDisableMaintenanceItem`
  （`:278`、`:317`、`:358`）；`docs/prd/business-logic-prd.md:132`/`:651` 与
  `docs/migration/current-database-schema.md:170` 写明「每车至少保留一个启用
  项目」。备份业务规则注释同样承诺与手工录入同一套规则，但此前只逐条
  `item.validate()`，没有按车分组检查。
- 证据级别：已复现（数据层用例先红后绿）。
- 触发路径：裸插一辆无项目的车（模拟被篡改/损坏的备份来源）→ 导出 → 恢复 →
  预校验逐条通过（项目段为空）→ 事务清库重插，零启用项目的车进库。
- 复现：`flutter test test/data/backup_restore_test.dart --plain-name 'car without enabled maintenance items'`
  — 修复前恢复成功；修复后通过。
- 根因：业务预校验缺少「按 carId 聚合启用项目」的跨行检查。
- 修复：项目逐条校验后按 carId 收集启用项目，逐车检查至少命中一个；不满足抛
  `LunioErrorException(backupInvalidData, '…至少需要保留一个启用的保养项目')`，
  仍在事务外。
- 测试夹具同步：本规则会让三条既有「用无项目车辆构造重复车辆」的用例提前
  命中业务预校验，分别给 `test/data/backup_restore_test.dart`（回滚用例）、
  `test/data/unique_constraint_test.dart`（payload 内重复车辆）、
  `test/widget/settings_test.dart`（恢复冲突对话框）的每辆车补一个启用项目，
  让它们继续走到表级唯一约束——保留原用例的验证意图，不降低覆盖。
- 回归：`flutter test test/data/backup_restore_test.dart test/data/unique_constraint_test.dart test/widget/settings_test.dart`
  全部通过。
- 提交：dbb16d7

### 3. 回前台不对账系统通知权限

- 位置：`lib/features/shell/reminders/notification_sync_controller.dart:251`
- 症状：用户在系统设置里重新打开通知权限后回到 App，`systemNotificationsEnabled`
  偏好仍为 false；系统 lane 读到关闭后直接取消调度，保养/里程提醒不会恢复。
  只有手动打开通知设置 sheet（load 里对账）才会修正。
- 错误依据：同文件 `syncFromProviders` 注释（约 284–286 行）明确「权限链…
  『请求过 → 对账系统真实开关』这半在回前台、数据完全没变时也要跑（用户在
  系统设置里改过通知权限）」；`onAppResumed` 此前只调
  `syncParkingLiveActivity()` + `_engine.invalidateInAppLane()`，没有任何权限
  对账；控制器测试也只锁了实时活动对账。
- 证据级别：已复现（controller 用例先红后绿）。
- 触发路径：偏好 `systemNotificationsEnabled=false` + `systemNotificationPermissionRequested=true`
  （模拟首启拒绝后用户去系统设置重新授权）→ 启动不触发对账 → `onAppResumed()`
  → 偏好仍 false。
- 复现：`flutter test test/features/notification_sync_controller_test.dart --plain-name 'resume reconciles the real switch'`
  — 修复前最后一次断言 `Expected: <true> / Actual: <false>`；修复后通过。
- 根因：回前台路径没有调用首启权限链的对账分支；数据没变时订阅也不会触发
  `syncFromProviders`，所以系统授权变化永远读不到。
- 修复：`onAppResumed` 增加 `_ensureInitialSystemNotificationPermission()`（已请求
  过 → 只对账系统真值并回写偏好、bump 纪元；没请求过 → 保持首启请求语义）。
  偏好写回后订阅自然触发下一轮同步并恢复调度；同步更新方法注释与
  `docs/operations-manual.md` 6.2 的回前台职责描述。
- 回归：`flutter test test/features/notification_sync_controller_test.dart` 14 用例
  全部通过（含原「回前台再对一次实时活动」用例）。
- 提交：ea8c64b
