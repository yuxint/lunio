- 用户补充：目标车为东风本田第十一代思域 2022 款（中国），原厂 App「智导互联 / Honda CONNECT 3.0」可显示油量、远程控车/开空调/锁车。用户要求本轮只调研硬件，软件等硬件到货后再议。
- 交付物：`十一代思域-OBD硬件调研与采购清单.md`（工作区根目录）。
- **决定性事实 1**：东风本田官方用户手册原文确认该车为**间接式 TPMS**（比较滚动半径与旋转特性，只报警、需 40–100 km/h 累计约 30 分钟校准）。汽油版与 e:HEV 措辞一致，全系无胎压数值。任何 OBD 手段都读不到四轮胎压。
- **决定性事实 2**：OBDb `tests/test_cases/2022/command_support.yaml` 记录 `7E0.012F:FLI` unsupported，`DA10` / `DB33`（29-bit 扩展寻址）下 `012F:FLI` supported，`DA60.60.227029:CIVIC_FLV` supported。本田需 29-bit 头（`ATSH DB 33 F1`，默认 `ATCP 18`）。OBDb 未标市场，以北美为主，中国版须实测。

## 后续：用户放弃胎压，只问油量

- 用户明确「胎压我可以不需要，但是油量有办法拿到吗」。已放弃胎压，目标收窄为油量。
- **关键修正**：上一轮验收步骤第 5 步漏了协议切换。ELM327 必须先 `ATSP 7`（ISO 15765-4 CAN 29-bit 500 kbit/s），再 `ATSH DB 33 F1`，然后 `012F`。`ATSP 7` 下默认功能头就是 `0x18DB33F1`，`ATSH` 与 `ATCP 18` 均可省。响应 `41 2F xx`，油量 % = `xx × 100 / 255`。
- **最简单的免代码路径**：Car Scanner 免费版「高级设置 > ECU 协议」从 6（11-bit 500K）改为 7（29-bit 500K），内置 Fuel Level 传感器即可出数。若无数据，自定义 PID：Command `012F`、Header 留空、Formula `A*100/255`、单位 `%`。

- 备选路径：私有 DID `DA60.60.227029:CIVIC_FLV`（supported 但公式未公开）；`DA10 222623`/`222678` 含 Fuel Level 但未解码；`DA10.10.222516` 带 2015 年份过滤，2022 不可用。

## 后续：确认 240TURBO 汽油版，问「208 组过滤器是什么」

- 用户明确：EV 唤醒不需要，车是 **240TURBO 汽油版**（不是 e:HEV）。**主推型号已从 Vgate iCar Pro 2S 改为 iCar Pro BLE 4.0**（官方 $33.99 ≈ ¥228，国内约 ¥90–150 未确认；官方规格同样列 29bit/500K，休眠约 3 mA）。2S 的 BLE 5.2 3 Mbps、EV 远程唤醒、208 组过滤器三项溢价点均用不上。
- **208 组过滤器解释**：Vgate 官方 2S 页原文 `Up to 208 sets of filters for passing, blocking, and flow control`，Amazon 文案注明 `for your hybrids or EVs`。CAN 是广播总线，500 kbit/s 满载每秒数千帧，BLE 上行带宽远小于总线吞吐，芯片必须先用验收过滤器（filter + mask）筛掉无关 CAN ID，否则缓冲溢出丢帧。208 = 可同时保存的规则条数，三类：pass（放行，`ATCF`/`ATCM`）、block（阻断，STN `STFAB`）、flow control（ISO-TP 多帧自动回流控帧，`ATCFC0/1`、STN `STFAFC`）。标准 ELM327 只有一组 filter + 一组 mask；ELM327 手册 p.41 原话 `Quite likely, you will never have to use the CM and CF commands.`
- 本需求用不上的理由：请求→响应模式，固件按协议 7 自动设默认接收过滤只收 `18 DA F1 xx`；不监听原始 CAN（`ATMA`/`STM`）；只读一个 PID；汽油车报文种类少于混动/纯电。
- 易混淆点：验收命令里的 `ATCRA`（不带参数）是标准 ELM327 复位默认过滤，与 2S 的 208 组高级规则不是同一层。
- 诚实说明：2S $37.99 vs BLE 4.0 $33.99，差价仅约 $4，降级精简功能但省钱有限；要明显降本必须选国产 v1.5 BLE（¥30–80 未确认），代价是 29-bit 稳定性风险。
- 已更新 `OBD硬件-下单决策单.md`：结论、第 2 节下单清单（主推改 BLE 4.0，2S 降为可选升级）、第 7 节未确认、8.3 车型条件、新增 8.7 节完整解释。

## 后续：用户问 2S 多了哪些功能、自己能自定义实现哪些

- 决策单新增 8.8 节「2S 相对 BLE 4.0 的差异，以及自研能补回什么」。
- **2S 官方唯一承认的「新增」是 EV / 混动远程唤醒**（Vgate 官方页原文 `has added the automatic wake-up function of electric vehicles`；BLE 4.0 官方页写 `Electric vehicles are not supported this function`）。汽油车用不上。
- 其余多项为营销文案或口径差异：3 Mbps 是内部 UART `baudrate`，不是 BLE 空口速率（LE 2M PHY 上限 2 Mbps）；208 组过滤器官方写 filters、第三方写「208-Byte OBD Buffer」，与 vLinker MS 文案重合，数量与实现未确认；过压/过温/过流保护 BLE 4.0 同系列手册同样列；Windows 支持与「更多第三方 App」是 SKU 口径/营销；固件升级、ELM327 v2.3、29bit/500K、休眠 3 mA 两者相同；主控芯片两款官方都不公布；2S 是否支持 ST 命令集未确认（明确支持的是 vLinker 系列）。
- **标准 ELM327 命令层两者共有**：`ATCF`/`ATCM`/`ATCRA`/`ATCFC0|1`/`ATMA`/`ATSH`/`ATCP`/`ATSP 7`/`ATST`，源自 Elm Electronics 官方数据手册。切 29-bit、设过滤、监听 CAN 都可由自研 App 下发，与型号无关。标准 ELM327 只有一组 mask + 一组 filter，208 条属固件扩展、无标准命令写入。
- 可自研补回：初始化序列、轮询调度/限频/超时、软过滤、ISO-TP 组包（默认 `ATCAF1`/`ATCFC1` 已做）、`A*100/255` 换算与去抖、缓存、断连重连、状态机、后台恢复。
- 部分可补但有代价：208 条硬件规则→软过滤需所有帧先到手机；EV 唤醒必须人工插拔；3 Mbps 只能靠降轮询频率消除需求。
- 不可补回：BLE 5.2 射频/LE 2M PHY/内部 UART、208 条硬件过滤表、EV 唤醒电路、保护元件、电流。
- **认知纠正**：写 App 补不回硬件能力，但本需求用不上这些能力。`012F` 响应仅 `41 2F XX` 几字节，请求-响应模式固件自动只回目标 ECU，一组 `ATCRA` 足够，汽油车点火时自动启动。
- 真正值得自研的是两款都不提供的：29-bit 自动切换与失败回退、油量去抖、熄火前末值缓存、加油检测、断连恢复、按 VIN 匹配车型配置。

## 后续：问后续开发能否不接 OBD

- 操作卡新增第 6 节「后续开发能否不接 OBD」，原第 6 节改第 7 节。
- **结论：绝大多数开发可离线，但必须先做一次真机实测**（nRF Connect 那次会话不可跳过，它决定项目是否成立）。
- **纠正前提**：nRF Connect 拿不到「所有响应」，只录到实际发过命令的返回（ELM327 是请求-响应模式）；Logs 可导出 CSV/Text 但**无回放功能**；导出是静态快照，油量值固定，验不了去抖/加油检测/轮询限频/超时重试；正常路径之外（NO DATA、?、分块、断连、乱码）录不到。正确做法是把日志整理成 fixture / scenario，而非回放固定日志。
- 可离线：AT 状态机、29-bit 头、`41 2F xx` 解析、轮询调度、滤波去抖、加油检测、UI、缓存持久化、错误处理、单测与 CI。必须真机或仿真外设：BLE 扫描/连接/服务发现/UUID、配对绑定、MTU 协商、写入类型、实车 29-bit 响应（一次）、真实时序、断连休眠。
- **iOS Simulator 无蓝牙**：CoreBluetooth 层要么用 CoreBluetooth-Mock，要么真 iPhone + 真实 BLE 外设。
- **推荐架构**：`OBDTransport` / `CentralStack` 协议，三实现（生产 CoreBluetooth / 调试 TCP / 测试 Mock+Fixture），上层解析不依赖传输层。类比后端 WireMock / Mockito 替第三方 API + 录制 HTTP 响应做 fixture。
- **工具**：`qadanm/elmulator`（MIT）三模式 —— in-process `Conversation`（无 socket 无射频）、TCP `elmulator serve --port 35000`、macOS `swift run elmulator-ble`（真实 BLE 外设供真 iPhone 连）；另有 `ElmulatorMockPeripheral` 桥接 CoreBluetooth-Mock 让生产 CBCentralManager 代码跑在 macOS CI。JSON scenario 支持分块/延迟/抖动/stall/断连/乱码，带 `expected_scan_summary` 回归断言。`Ircama/ELM327-emulator` 是 RFCOMM/SPP 且 CC BY-NC-SA 禁商用，iOS 不适用。
- 建议顺序：真机实测导出日志 → 整理 `.scenario.json` → 补异常场景 → MockTransport 开发业务层与 UI 跑 CI → elmulator-ble 验 BLE 链路 → 发布前真车复测 2–3 次（不同油量、冷热车、点火/熄火）。
