## 油箱容量偏差：用户指出官方手册为 47 L

- 用户指出官方手册写明油箱容积 **47 L**，与导出的 50 L 有偏差。**核实无误**：东风本田《2022 思域用户手册》「燃油信息」原文「■ 燃油箱容量: 47L」（https://www.dongfeng-honda.com/car/civic/manual/2022/42T40C000/html/b742474d58fb.html ）；官网车型对比页「油箱容积(L) 47」；易车、中华网 2022 款 240TURBO 各配置参数表均为 47。
- **偏差量化**（pct = 96/255 = 37.6470588%）：50 L 设定 → 18.823529 L / 自由 31.176471 L；47 L → 17.694118 L / 自由 29.305882 L；差 **1.129412 L（高估 6.38%）**，等于 50/47 的比值偏差。
- **核心澄清**：这不是数据错误，而是印证「容量是 App 设定值」。ECU 只报百分比（PID `2F`，A=`0x60`），升数由 App 用设定容量乘出来。偏差只发生在 App 计算值上，**不影响 PID `2F` 百分比读数，也不影响自研 App 读油量**。
- **精度边界（主动提醒）**：即使按 47 L，升数仍是估算。PID `2F` 是油浮子位置的归一化百分比，厂商标定未必线性对应容积；手册明确加油枪跳停后预留燃油膨胀空间；油箱底部有不可用余量；油面晃动会带来波动。百分比可靠，升数只作参考。
- **自研 App 要求**：容量做成可配置项，默认 47 L，**不得硬编码 50 L**；UI 上把升数标为估算。可选：加满/低油量两点标定建立映射。
- **可验证实验**：在 Car Scanner 设置里把油箱容量由 50 改为 47，重新录制导出；若升数变为约 17.69 L，即直接证明容量是设定值。
- 文档已更新：操作卡「导出数据分析」节补 47 L 核实、偏差量化、自研要求、验证实验、精度边界；依据节加入官方手册链接。

## nRF Connect 操作讨论：UTF-8 与批量发送（用户实操前确认）

- 用户质疑两点：①「他这个不支持 utf-8 格式吗」②「不能一次性发送指令吗」。这是要修正操作卡措辞，不是新需求。
- **① UTF-8：支持。操作卡原句理由写错，已改。** Nordic Developer Academy Lesson 4 Ex3 iOS 段原文 `Select UTF8 to send a string. Type a message in the box, select the type of operation: Request (write with response) or Command (write with no response), and press Write.` 真正障碍是 CR：iOS 键盘 Return 产生 LF (0x0A) 或直接收键盘，ELM327 只认 CR (0x0D)；nRF Connect iOS 未找到「自动追加 \r」开关（未确认有）。ELM327 忽略所有控制字符含 LF，CRLF 可用、纯 LF 会 20 秒后回 `?`。所以 HEX/字节模式把 0D 编进末字节仍最稳。格式标签字面名（`HEX` / `ByteArray`）**未确认**，以实机为准。iOS 按钮是 `Write`，`SEND` 是 Android。
- **② 一次性发送：不能，操作卡「逐条发 + 等 >」正确。** ELM327 官方手册：`all messages ... must be terminated with a carriage return (hex '0D')`；`The memory buffer only remembers the one last command - there is no provision ... for any more`；处理期间到达的 RS232 字符会**中断**而非排队；`software should always wait for either the prompt character ('>') ... before beginning to send the next command`。`ATZ` 等同断电重启，会丢同包后续字节并把 ATE0/ATL0 恢复默认；`ATSP 7` 非零协议立即写 EEPROM（约 30 ms），须等 `OK`。
- 另两层约束：iOS 版 nRF Connect **无 Macro**（Nordic 官方博客 2017「macros (currently Android only)」，2026 App Store 功能列表仍无）；单次写入上限 = `maximumWriteValueLength`（默认 ATT_MTU 23 → 20 字节），整套序列 26 字节装不下。
- **唯一合法合并**：CAN 一条 OBD 报文最多请求 6 个 PID（手册 `Multiple PID Requests`，例 `01 04 05 0B 0C`），只能合并数据采集请求，不能合并 AT 初始化命令。
- 省点击办法：跳过非必需的 `ATL0`（只关响应 LF）；或换 **BlueTerm: Bluetooth Terminal**（中国区免费，App ID `6812643249`，开发者 `mint-soft`，含广告，Pro 买断 ¥48，iOS 15.0+，简体中文），其 App Store 描述称支持 `CR` 行尾、免费版 1 条带延时命令序列、GATT explorer 自定义 UUID —— 功能与对本硬件兼容性均需实机验证；或用 Android 版 nRF Connect 的 Macro。
- 操作卡已改：B4 第 13 步（UTF8 支持 + CR 说明）、第 16 步（逐条发的协议依据）、新增 B7「能不能少点几次」。

## 命令含义教学（用户问四件事：什么意思 / 为什么 / 还有哪些 / 能否读所有信息）

- 8 条命令分三层：`ATDPN`/`ATZ`/`ATE0`/`ATL0`/`ATI` 配置适配器（不读车）；`ATSP 7` 设协议（决定 CAN 通道）；`0100`/`012F` 才是发给 ECU 的请求。**只有 `012F` 返回了车辆数据**，其余都不是车辆信息。
- 逐条：`ATDPN` 按编号描述当前协议（A 前缀=自动探测）；`ATZ` 全复位返回版本串；`ATE0` 关回显；`ATL0` 关响应换行；`ATI` 打印版本 ID 不复位（与 ATZ 返回的版本串有冗余，可省）；`ATSP 7` = ISO 15765-4 CAN 29-bit 500K，非零协议写 EEPROM；`0100` 支持位图；`012F` 油量。
- **关键纠正（已写入操作卡）**：`0100` 的 4 字节位图只覆盖 PID `01`–`20`，**不含 `2F`**。`2F` 属于 `21`–`40` 段，其支持位图是 `0120`（`30 31 32 30 0D`）。SAE J1979 分段：`0100`→01-20、`0120`→21-40、`0140`→41-60、`0160`→61-80、`0180`→81-A0、`01A0`→A1-C0。`0100` 同时是标准的 initialization/keep-alive/ping。
- 多 PID 请求规则（SAE J1979 原文）：一条请求最多 6 个 PID；**不得把支持位图 PID 与数据 PID 混在一条请求里**；响应中 PID 顺序不保证与请求一致（自研 App 解析要注意）。
- 其他命令分类：会话/输出 `ATWS`(暖启动) / `ATD`(恢复默认) / `ATH1`(显示 CAN ID) / `ATS0`(关空格) / `ATST hh`(超时 4ms 步进) / `ATAT1`(自适应时序) / `ATTP 7`(Try Protocol 不写 EEPROM) / `ATPC`；诊断 `ATRV`(读 OBD 口电压，独立于车辆应答，排障首选) / `ATIGN` / `03` / `07` / `0A` / `02` / `06` / `0902`(VIN 多帧) / `090A`；实时 PID `010C` 转速 / `010D` 车速 / `0105` 水温 / `010F` 进气温度 / `0110` MAF / `0111` 节气门 / `0104` 负荷 / `0142` 模块电压 / `01A6` 里程；CAN 层 `ATMA` / `ATMR` / `ATMT` / `ATCF` / `ATCM` / `ATCRA` / `ATCSM1` / `ATSH` / `ATCP`；厂商扩展 Mode 22 / UDS `10 03` / `27`。`04` 清码有副作用，不得随意发。
- **不能读到所有信息**：立法 OBD 只覆盖排放相关；本车 OBD 口经网关隔离（DIAG-CAN），看不到主干 F-CAN/B-CAN；胎压数值车上不存在；车身状态、远控、ABS/SRS/TCU 需厂商私有通道。OBD 口是标准化只读诊断窗口，不是整车数据总线导出接口。
- 操作卡 B4 段补入 `0100` 覆盖范围与 `0120` 说明。已用一张 SVG 图向用户解释命令分层与数据边界。

## 油量指令依据与其他获取路径（用户追问「为什么用 012F」）

- **规范依据**：SAE J1979 / ISO 15031-5 定义 Service 01 PID `2F` = Fuel Tank Level Input，1 字节 A，公式 `A × 100 / 255`，单位 %，是 Mode 01 **唯一**的油箱液位 PID。响应 SID `41` = 请求 `01` + `0x40`。ELM327 只做协议转换与透传，不解码。python-OBD 源码 `OBDCommand("FUEL_LEVEL", "Fuel Level Input", b"012F", 3, percent, ECU.ENGINE, True)`；其 Mode 02 自动克隆为 `DTC_FUEL_LEVEL` = `022F`（标准 J1979 三字节写法是 `022F00`，含 FRNO 帧号）。
- **实车依据**：OBDb `Honda-Civic/tests/test_cases/2022/command_support.yaml` 中 `DA10.012F:FLI` 与 `DB33.012F:FLI` 为 supported，`7E0.012F:FLI` 为 unsupported；用户 Car Scanner 实测 37.6471% = `0x60`。注意 `7E0` 段大量 PID 同为 unsupported，说明该测试在 29-bit 环境完成。
- **重要修正**：上一轮「车上没有升数」的宽泛说法不成立。OBDb `signalsets/v3/default.json` 定义 `DA60.60.227029`（hdr `DA60`, rax `60`, cmd `22 7029`, filter `from:2015`）→ `CIVIC_FLV`，`fmt: {bix:96, len:16, max:655, div:100, unit:"liters"}`，2022 command_support 中为 **supported**。Car Scanner 显示的 18.8235 L 仍来自设定容量换算（37.6471% × 50 L），与该 DID 来源不同。中国版实车响应未验证。
- 其他本田私有油量 DID（均 2022 supported、未解码、仅抓首字节）：`DA10.10.222623` 描述含「Fuel Level」，`DA10.10.222678` 含「Fuel Level(Average)」平均值。`DA10.10.22268E` 是燃油**压力**不是液位。
- **不得使用**：`DA10.10.222516`（`CIVIC_FLI_INPUT`）与 `DA10.10.22F42F`（`CIVIC_FLI_F4`），带 2015 年份限定，2022 记录为 unsupported。注意 `DA60.000060.227029`（8 字节/扩展头写法）也 unsupported，要用 `DA60.60.227029` 形式。
- 相关但非液位（2022 supported）：`019D:FUEL_RATE_ALT,VFUEL_RATE`（燃油率，可积分估算但误差累积）、`0151:FUEL_TYP`、`0152:ALCH_PCT`、`0103:FUELSYS1,FUELSYS2`、`0123:FRP`、`01A6:ODO`。python-OBD 另有 `015E` `FUEL_RATE`。
- 私有 DID 需 29-bit 物理寻址（如 `ATSH DA 60 F1`）+ ISO-TP 多帧 + 接收过滤，复杂度远高于 `012F`，仅在标准 PID 数值不稳时再评估。

## 实机反馈：UTF8 模式写入 ATDPN 无效（第一条命令的失败样本）

- 用户用 `UTF8` 格式写入 `A​T​D​P​N` 后发来 nRF Connect Log 截图。日志：`Writing value '41E2 808B 54E2 808B 44E2 808B 50E2 808B 4EE2 808B' to Electric Current Statistics Characteristic` / `Wrote 41e2808b54e2808b44e2808b50e2808b4ee2808b to 2AF1 Characteristic`。
- **解析结论：写入无效，命令不会执行。** 实际 20 字节 = `41 [E2 80 8B] 54 [E2 80 8B] 44 [E2 80 8B] 50 [E2 80 8B] 4E [E2 80 8B]`。每个字母后跟一个 UTF-8 的 **U+200B 零宽空格**（`E2 80 8B`），从聊天/网页复制文本时带入。正确应为 6 字节 `415444504E0D`。
- 两个致命点：① **无 `0D` 结尾**，ELM327 只认 CR 作命令结束符，会等待约 20 秒后回 `?`；② 高字节 `E2 80 8B` 不是合法 AT 命令字符。零宽空格还把 5 字节撑到 20 字节，正好撞默认 ATT_MTU 23 的单包上限。
- **UTF8 / Text 路径在 iOS 上走不通**：键盘回车只产生 LF `0A`，nRF Connect 无自动追加 `\r` 开关。必须切 `HEX` / `ByteArray`。
- 日志中只有 `Writing value` 与 `Wrote`，**没有 `2AF0` 的通知记录**。已提醒用户先回 Client 页确认 `2AF0` 的 ↓ 已订阅，否则命令发对了也看不到返回。
- 文档已改：3.4 第 13 步补入「UTF8 无法输入 CR、复制文本可能带 U+200B」；排错表新增两行（「只有 Wrote 无返回」→ 缺 `0D`；「Wrote 里出现 `E2 80 8B`」→ 零宽空格）。

## 实机反馈：Byte Array 写入框显示 N/A

- 用户切到 `Byte Array`，填 `415444504E0D`，输入框右下角显示灰色 `N/A`，以为识别不了。**判断：写法正确，`N/A` 不是字节解析失败，直接点 `Write` 即可。**

## 里程碑：第一条实测数据到手，ELM327 链路打通

- 日志（19:18:15–19:18:49）：
  - `Setting Boolean true for Notifying Characteristic Electric Current Specification` → **`2AF0` 通知订阅成功**（此前一直担心的点已排除）
  - `Wrote 415444504e0d to 2AF1 Characteristic` → **6 字节写入完全正确**，含末字节 `0D`
  - `Updated Value of Characteristic 2AF0 to 370D 0D3E.` / `"370D 0D3E" value received.` → **收到响应**
- **解析 `37 0D 0D 3E`**：`37` = ASCII `'7'`，两个 `0D` = CR，`3E` = `'>'`。即 `ATDPN` 返回 **`7`**。
- **`7` 的含义**：手动指定的协议 7 = ISO 15765-4 CAN 29 bit ID / 500 kbaud。无 `A` 前缀，不是自动探测（自动应为 `A7`）。来源：Car Scanner 步骤 A 手动选协议 7 后由 `ATSP` 写入 EEPROM，适配器记住了。
- **两点结论**：① 与 OBDb 2022 数据一致 —— 这台车油量确实要走 29-bit；② 这是 EEPROM 记忆，脆弱，自研 App 必须在初始化序列里显式 `ATSP 7`，不得依赖。之前的推断得到实车证实。
- **下一步操作风险（已写入文档表 1 说明）**：`ATZ` 会把协议复位回自动，表 1 第 7 步 `ATSP 7` **不得跳过**，否则 `012F` 返回 `NO DATA`。`ATE0`/`ATL0` 必须在 `ATZ` 之后发（表中顺序已正确）。
- 期望下一条关键响应：`012F` → `41 2F xx`。Car Scanner 此前读数 37.6471%，若油量未变，原始字节应接近 `60`；加油后会不同，只作对照。
- 文档改动：表 1 说明补入「`ATZ` 复位协议、`ATSP 7` 不得跳过」。文档仍保持「全部指令待实测」状态，等完整日志到手后统一整理。
