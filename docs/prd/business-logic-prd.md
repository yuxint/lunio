# Lunio 业务逻辑说明

## 1. 文档定位

本文档用于沉淀 Lunio 当前 Flutter 版本的业务逻辑，重点说明代码里不容易直接看出的规则、边界和数据口径。

本文档描述当前代码事实，不定义未来愿景。后续修改提醒、通知、频率、保养记录、车辆上下文、备份恢复或日期逻辑时，应先检查本文档是否需要同步更新。

## 2. 产品边界

Lunio 是本地优先的车辆保养记录 App。当前主业务围绕一辆“当前应用车辆”展开，用户可以维护车辆、配置保养项目、记录保养历史，并查看保养提醒。

当前已落地能力：

- 车辆管理。
- 当前应用车辆。
- 保养项目配置。
- 保养记录新增、编辑、删除和筛选。
- 保养提醒进度计算。
- App 内提醒弹窗。
- 系统本地通知调度。
- 提醒页停车倒计时。
- JSON 备份导出和恢复。
- 开发者模式下的手动日期。
- 浅色、深色和跟随系统主题。

当前不包含：

- 账号、登录和多用户。
- 云同步和服务端接口。
- 支付、订单、预约和门店。
- 图片附件、OCR 和保养单扫描。
- 多设备实时协作。
- iOS Live Activity、Dynamic Island 和 Widget Extension。

## 3. 数据版本和稳定标识

当前数据库 `schemaVersion` 为 5。当前备份 JSON `schemaVersion` 为 2。

稳定标识口径：

- 所有核心业务对象使用 64 位整数 ID。
- 车辆主键是 `cars.id`。
- 车型默认保养项目模板主键是 `vehicle_default_maintenance_items.id`。
- 内置车型和默认保养模板通过 `catalog_id` 保存内置 JSON 稳定标识；它只用于 bootstrap 同步，不进入备份契约。
- 车辆内实际保养项目主键是 `maintenance_items.id`。
- 保养记录主键是 `maintenance_records.id`。
- 保养记录和保养项目通过 `maintenance_record_items` 关联。

注意：

- 不要把展示文案当作稳定主键。
- 当前内置目录稳定标识字段名是 `catalog_id`，不是 `catalogKey`。
- 当前 `maintenance_items` 没有 `isDefault` 字段。
- 车型默认模板和车辆内实际保养项目是两张表，不要混用。

## 4. 核心业务对象

### 4.1 车辆

车辆字段包括：

- ID。
- 品牌。
- 车型。
- 当前里程，单位公里，整数。
- 上路日期，业务日期格式为 `yyyy-MM-dd`。
- 同步元数据。

当前唯一性：

- `cars` 表唯一约束为 `brand + model + roadDate`。
- 这意味着同品牌同车型只要上路日期不同，当前数据库允许同时存在。

关键规则：

- 当前里程不会因为新增或编辑保养记录而回退。
- 保存记录时，如果记录里程大于车辆当前里程，则抬高车辆当前里程。
- 删除车辆会清理该车的保养记录、记录项目关联和保养项目。
- 删除当前应用车辆后，会重新解析当前应用车辆。

### 4.2 当前应用车辆

当前应用车辆是提醒页、记录页和新增记录的共享业务上下文。

解析规则：

- 当前应用车辆 ID 存在 `app_preferences.appliedCarId`。
- 如果偏好值为空、非法或指向已删除车辆，回退到车辆列表第一辆。
- 如果没有车辆，当前应用车辆为空，并写回空偏好。

使用范围：

- 提醒页只计算当前应用车辆。
- 记录页只展示当前应用车辆的记录。
- 新增保养记录默认只在当前应用车辆范围内操作。
- 切换当前应用车辆后，要同步刷新车辆、保养项目、保养记录和提醒。

### 4.3 保养项目

保养项目表示某辆车可维护和可提醒的一类项目，例如机油、空调滤芯、刹车油。

字段包括：

- ID。
- 归属车辆 ID。
- 名称。
- 是否启用。
- 是否按里程提醒。
- 里程提醒间隔，单位公里。
- 是否按时间提醒。
- 时间提醒间隔，单位月。
- 到期阈值 `notOverdueUpperLimit`，默认 100。
- 超期阈值 `overdueUpperLimit`，默认 125。
- 排序值。
- 同步元数据。

校验规则：

- 名称不能为空。
- 同一车辆内项目名称唯一。
- 至少开启一种提醒方式。
- 开启按里程提醒时，里程间隔必须大于 0。
- 开启按时间提醒时，时间间隔必须大于 0。
- 禁用或删除项目时，必须保证该车至少仍有一个启用项目。
- 有历史记录关联的项目不能删除。

启用状态影响：

- 禁用项目不出现在新增记录的默认可选项中。
- 编辑历史记录时，如果原记录包含已禁用项目，该项目仍会显示，避免历史记录无法编辑。
- 禁用项目不参与提醒页和通知候选计算。

### 4.4 车型默认保养项目

车型默认保养项目是创建车辆或恢复默认配置时使用的模板。

字段包括：

- ID。
- 品牌。
- 车型。
- 项目名称。
- 提醒方式和间隔。
- 到期和超期阈值。
- 排序值。
- 同步元数据。

关键规则：

- 默认模板不直接等同于某辆车的实际保养项目。
- 创建车辆时，会按当前车型模板复制一份 `maintenance_items`。
- 恢复默认项目时，先回填页面草稿；最终由保存车辆动作统一写库。
- 车型模板唯一约束为 `vehicleBrand + vehicleModel + itemName`。

### 4.5 保养记录

保养记录表示某车在某天发生的一次保养。

字段包括：

- ID。
- 车辆 ID。
- 保养日期，格式为 `yyyy-MM-dd`。
- 项目 ID 列表。
- 费用，单位分，非负整数。
- 保养发生时里程，单位公里，非负整数。
- 备注。
- 同步元数据。

关键规则：

- 一条记录可以包含多个保养项目。
- 项目列表会按 ID 去重，保持原顺序。
- 一条记录至少包含一个项目。
- 同一车辆同一日期只能有一条保养记录。
- `maintenance_record_items` 保证同一车辆同一天同一项目只能出现一次。
- 保养记录只能引用同一车辆下的项目。
- 删除整条记录会删除记录项目关联。
- 从项目维度删除时，如果原记录只剩一个项目，则删除整条记录；否则只移除该项目。

## 5. 日期上下文

所有业务日期使用 `LocalDate`，标准格式为 `yyyy-MM-dd`。

日期规则：

- `LocalDate.parse` 严格校验格式和自然日期。
- 如果输入 `2026-02-30` 这类无效日期，会抛出格式异常。
- 月份加法会按目标月份最大天数收敛，例如 1 月 31 日加 1 个月会落到 2 月最后一天。
- 天数差使用自然日差。

“今天”的来源：

- 默认来自系统日期。
- 开发者模式关闭时，手动日期不生效。
- 开发者模式开启、`manualDateEnabled=true` 且 `manualDate` 合法时，业务今天使用手动日期。

受手动日期影响的逻辑：

- 车龄展示。
- 保养时间进度。
- 提醒页状态。
- App 内通知当天确认和 15 天延后判断。
- 系统通知重排签名中的 today。

## 6. 保养提醒计算

提醒计算入口集中在 `MaintenanceRules.progressForItem` 和 App 壳层的提醒视图组装逻辑。

### 6.1 数据范围

提醒页按当前应用车辆计算：

- 使用当前应用车辆。
- 使用该车所有启用且有 ID 的保养项目。
- 使用该车保养记录。
- 使用 `effectiveTodayProvider` 得到的今天。

如果没有车辆或数据仍在加载，提醒页走空态或加载态。提醒页顶部概览在没有保养记录时显示“暂无”，不会用上路日期伪造最紧急项目。

### 6.2 最近保养记录

每个项目独立寻找最近一次保养记录：

- 只看 `record.itemIds` 包含该项目 ID 的记录。
- 日期更晚的记录优先。
- 日期相同时，里程更高的记录优先。
- 找不到历史记录时，最新记录为 null。

一条多项目保养记录会同时成为多个项目的最近记录候选。

### 6.3 里程进度

项目开启按里程提醒时才计算里程进度。

计算规则：

- 基准里程 = 最近保养记录里程；无历史记录时为 0。
- 已使用里程 = 当前车辆里程 - 基准里程。
- 如果已使用里程小于等于 0，则进度按 0 处理。
- 里程进度百分比 = 已使用里程 / 里程间隔 * 100。
- 剩余里程 = 里程间隔 - 已使用里程。

展示规则：

- 剩余里程大于 0：显示距离下次约多少公里。
- 剩余里程等于 0：显示里程已到期。
- 剩余里程小于 0：显示已超多少公里。

### 6.4 时间进度

项目开启按时间提醒时才计算时间进度。

计算规则：

- 基准日期 = 最近保养记录日期；无历史记录时为车辆上路日期。
- 到期日期 = 基准日期 + 时间间隔月数。
- 总天数 = 基准日期到到期日期的自然日差。
- 已过天数 = 基准日期到今天的自然日差。
- 剩余天数 = 今天到到期日期的自然日差。
- 如果总天数小于等于 0，或已过天数小于等于 0，则进度按 0 处理。
- 时间进度百分比 = 已过天数 / 总天数 * 100。

展示规则：

- 剩余天数大于 0：显示距离下次约多少天、月或年。
- 剩余天数等于 0：显示时间今日到期。
- 剩余天数小于 0：显示已超多久。

### 6.5 综合进度和状态

综合规则：

- 同时开启里程和时间提醒时，取百分比更高的一项作为主进度。
- 只开启一种提醒方式时，使用该方式进度。
- 未开启任何提醒方式在实体校验层会被拒绝。

状态规则：

- `percent >= overdueUpperLimit`：超期，`danger`。
- `percent >= notOverdueUpperLimit`：到期，`warning`。
- 其他情况：正常，`normal`。

默认阈值：

- 到期阈值默认 100。
- 超期阈值默认 125。

展示百分比：

- 原始进度可超过 100。
- 展示百分比会四舍五入。
- 如果原始进度还没真正达到阈值，展示值不会因为四舍五入提前显示为阈值，例如 99.6 不显示为 100%。
- 展示文本超过 999 时显示为 `999%+`。

### 6.6 提醒排序

提醒页行排序规则：

- 状态越严重越靠前：超期、到期、正常。
- 状态相同时，进度百分比更高的靠前。
- 仍相同时，按项目 `sortOrder` 升序。

## 7. 通知业务逻辑

Lunio 当前有两类通知：

- 系统本地通知：由 `flutter_local_notifications` 调度。
- App 内通知：打开 App 后弹出 Lunio 自定义对话框。

两者都复用同一套保养提醒计算结果，但触发和抑制方式不同。

### 7.1 通知设置

通知设置来自 `notificationSettingsProvider`。

偏好 key：

- `systemNotificationsEnabled`：系统通知，默认开启，只有值为 `false` 时关闭。
- `inAppNotificationsEnabled`：App 内通知，默认开启，只有值为 `false` 时关闭。
- `maintenanceDueEnabled`：保养到期提醒，默认开启，只有值为 `false` 时关闭。
- `maintenanceDueRepeat`：保养到期系统通知重复频率，默认 `weekly`。
- `systemNotificationPermissionRequested`：是否已请求过系统通知权限。

频率枚举支持：

- `daily`：服务层支持，但当前设置 UI 不展示。
- `weekly`：每周。
- `everyTwoWeeks`：每 2 周。
- `everyThreeWeeks`：每 3 周。
- `monthly`：每月。

解析注意：

- 当前 `ReminderRepeatFrequencyCodec.parse` 不解析 `daily`，未知值回退 `weekly`。
- 当前通知设置 UI 展示每周、每 2 周、每月，不展示每天。

### 7.2 系统通知权限

当系统通知设置开启时，App 壳层会在首帧后检查权限。

规则：

- 如果 `systemNotificationPermissionRequested=true`，不再主动请求。
- 如果未请求过，则调用系统权限请求。
- 请求完成后写入 `systemNotificationPermissionRequested=true`。
- 同时把 `systemNotificationsEnabled` 写为授权结果。
- 如果用户拒绝权限，系统通知设置会被写成关闭。

### 7.3 系统通知调度

系统通知同步由 App 壳层触发。

重排签名包含：

- 系统通知是否开启。
- 当前车辆 ID。
- 当前车辆里程。
- 当前车辆 `updatedAt`。
- 今天。
- 保养项目数量。
- 保养记录数量。
- 保养到期重复频率。

当签名变化时，重新调度系统通知。

调度规则：

- 每次重排先取消 ID 8000 到 8999 范围内的 Lunio 通知。
- 保养到期通知使用起始 ID 8000。
- 更新车辆里程通知使用起始 ID 8900。
- 停车倒计时到点通知使用固定 ID 9001。
- Android 停车倒计时常驻通知使用固定 ID 9002。
- 每条通知默认预排 8 次。
- 首次通知时间为本地时区下一个 09:00；如果今天 09:00 已过，则从明天 09:00 开始。
- 每周、每 2 周、每 3 周使用固定天数递增。
- 每月使用本地时区月份递增。
- 常规保养和里程更新通知会避开停车倒计时到点时间，避免与停车到点通知落在同一分钟。

系统通知内容：

- 如果存在未被抑制的到期或超期保养项目，生成一条“保养提醒”系统通知。
- 文案包含车辆、到期项目数量和最紧急项目。
- 如果车辆里程更新提醒到期且未被抑制，生成一条“更新车辆里程”系统通知。

### 7.4 App 内通知触发

App 内通知在壳层根据当前数据即时检查。

触发签名包含：

- App 内通知是否开启。
- 当前车辆 ID。
- 当前车辆里程。
- 当前车辆 `updatedAt`。
- 今天。
- 保养项目数量。
- 保养记录数量。

检查规则：

- `inAppNotificationsEnabled=false` 时不弹。
- 正在检查时不重复进入。
- 保养到期提醒先弹。
- 如果还有里程更新提醒，再弹“更新当前里程”。
- 用户操作后会清空系统通知和 App 内通知签名，促使后续重新评估。

### 7.5 保养到期通知候选

保养到期通知候选来自提醒页同一套行数据，但只取已到期或超期项目。

候选条件：

- `maintenanceDueEnabled=true`。
- 项目启用。
- 项目状态为 `warning` 或 `danger`。
- 项目没有被 15 天延后。
- 项目当天没有被确认过。

抑制 key：

- 延后到期日期：`maintenanceReminderSnoozedUntil:{itemId}`。
- 当天确认日期：`maintenanceReminderAcknowledgedOn:{itemId}`。

用户操作：

- 点击“知道了”：为本次弹窗里的所有保养通知候选写入当天确认日期。
- 点击“15 天内不再提醒”：为本次弹窗里的所有保养通知候选写入今天加 15 天。

### 7.6 车辆里程更新通知候选

车辆里程更新提醒用于提示用户更新车辆当前里程。

是否到期：

- 先根据该车保养记录推导里程更新频率。
- 再以车辆 `sync.updatedAt` 转成 `LocalDate` 作为上次里程更新时间。
- 今天大于等于下次提醒日期时，视为到期。

抑制 key：

- 延后到期日期：`mileageUpdateSnoozedUntil:{carId}`。
- 当天确认日期：`mileageUpdateAcknowledgedOn:{carId}`。

用户操作：

- 点击“知道了”：写入当天确认日期。
- 点击“15 天内不再提醒”：写入今天加 15 天。

注意：

- 车辆 `updatedAt` 不只在手动更新里程时变化；记录保存抬高车辆里程也会更新它。
- 如果车辆里程刚因记录保存被抬高，里程更新提醒会按新的 `updatedAt` 延后。

## 8. 停车倒计时

停车倒计时是提醒页里的临时高频工具，不属于车辆、保养项目或保养记录。

### 8.1 数据存储

存储规则：

- 停车倒计时保存在 `app_preferences.parkingCountdown`。
- 内容是 JSON，包含 `startedAt` 和 `durationSeconds`。
- `durationSeconds` 必须大于 0。
- `endsAt = startedAt + durationSeconds`。
- JSON 解析失败时按没有停车倒计时处理。
- 停车倒计时不进入备份 JSON；导出内容不包含 `parkingCountdown` 或其他 `app_preferences`。

清理规则：

- 用户点击结束倒计时会删除 `parkingCountdown`。
- 清空数据会删除所有 App 偏好，因此也会删除停车倒计时。
- 恢复备份会先清空 App 偏好，因此不会保留恢复前的停车倒计时。

### 8.2 进度和状态

计算入口是 `ParkingCountdownRules.progress`。

规则：

- 如果当前时间早于到点时间，按剩余毫秒计算剩余百分比。
- 剩余百分比大于 20：状态为正常。
- 剩余百分比小于等于 20：状态为即将到点。
- 当前时间达到或超过到点时间：状态为已超时。
- 超时时 `remainingSeconds=0`，并按超出时长计算 `expiredSeconds`。

展示规则：

- 提醒页只有存在停车倒计时时展示停车倒计时卡片。
- 停车倒计时卡片位于当前车辆卡片和保养提醒列表之间。
- 倒计时运行中，开始停车倒计时入口禁用，避免叠加多个倒计时。
- 入场时间使用时、分、秒滚轮选择。
- 免费时长使用整数分钟输入，快捷时长 chip 只是快速填值。

### 8.3 通知

系统通知开启时，保存停车倒计时会调度到点提醒。

通知规则：

- 保存新倒计时前先取消已有停车倒计时通知。
- 如果到点时间已经不晚于当前时间，不再调度到点通知。
- 到点通知标题为“停车倒计时”，内容提示免费停车时间已到。
- 到点通知 payload 为 `lunio:parkingCountdown`。
- Android 优先使用 exact alarm；无法使用精确闹钟时回退到 inexact 调度。
- Android 会额外展示 `lunio_parking_ongoing` 常驻通知，使用系统 chronometer 倒计时显示免费离场时间。
- 结束倒计时会同时取消到点提醒和 Android 常驻通知。
- 关闭系统通知、清空数据和恢复备份时，也必须清理停车倒计时通知。

当前仓库没有 iOS Live Activity、Dynamic Island 或 Widget Extension 接线，停车倒计时的系统外展示只按本地通知能力处理。

## 9. 频率计算逻辑

### 9.1 保养到期通知频率

保养到期系统通知频率直接来自用户设置：

- 默认 `weekly`。
- 当前设置 UI 可选每周、每 2 周、每月。
- 服务层还支持每天和每 3 周，但不是当前 UI 主路径。

当前 `_maintenanceRepeatFrequency` 不根据项目严重程度、超期天数或车辆使用强度动态调整，直接返回设置值。

### 9.2 里程更新提醒频率

里程更新频率由最近保养节奏推导。

输入：

- 当前车辆的保养记录列表。
- 只取记录日期，不看里程增量、不看费用、不看项目类型。
- 同一天多条记录按一个日期处理。

计算步骤：

1. 提取所有记录日期并去重。
2. 按日期倒序排列。
3. 如果不同日期少于 2 个，返回每月。
4. 最多取最近 5 个日期。
5. 计算相邻日期间隔天数。
6. 忽略非正间隔。
7. 对间隔取平均值。

频率映射：

- 平均间隔 `<= 10` 天：每周。
- 平均间隔 `<= 17` 天：每 2 周。
- 平均间隔 `<= 24` 天：每 3 周。
- 其他：每月。

到期日计算：

- 每天：上次日期 + 1 天。
- 每周：上次日期 + 7 天。
- 每 2 周：上次日期 + 14 天。
- 每 3 周：上次日期 + 21 天。
- 每月：上次日期加 1 个月，月底日期按 `LocalDate.addMonths` 收敛。

## 10. 保养记录流程

### 10.1 新增记录

新增记录表单分两步。

第一步填写：

- 保养日期。
- 保养里程。
- 费用。
- 备注。
- 保养项目，多选。

第一步校验：

- 保养里程必须是非负整数。
- 费用必须是非负数字。
- 至少选择一个保养项目。
- 新增时只展示启用项目。

第二步确认：

- 用户确认本次所选项目的下次提醒间隔。
- 保存后会同时更新本次保养项目的默认提醒间隔。

保存规则：

- 写入保养记录。
- 写入记录和项目关联。
- 同一事务内校验项目是否属于当前车辆。
- 同一事务内校验同车同日唯一。
- 同一事务内校验同车同日同项目唯一。
- 如果记录里程高于车辆当前里程，同步抬高车辆当前里程。

### 10.2 编辑记录

编辑记录也走两步流程。

编辑规则：

- 可修改日期、里程、费用、备注和项目集合。
- 原记录包含的已禁用项目仍可显示和保留。
- 保存时校验目标同车同日不能已有其他记录。
- 保存时重写该记录的项目关联。
- 车辆当前里程只会被更高记录里程抬高，不会回退。
- 只有所选项目允许在确认页同步更新提醒间隔。

### 10.3 按项目删除

按项目维度删除记录时：

- 如果原记录只有一个项目，删除整条记录。
- 如果原记录有多个项目，只删除当前项目关联。
- 原记录日期、里程、费用和备注保持不变。

删除保养记录不会自动回退车辆当前里程。

## 11. 保养项目和车辆配置流程

### 11.1 创建车辆

创建车辆时：

- 先创建车辆。
- 再按车型默认模板复制保养项目。
- 复制后的项目归属新车，拥有自己的项目 ID。

如果用户在新增车辆流程中调整项目配置，最终保存时应以页面草稿统一写入，而不是在恢复默认或编辑草稿时提前落库。

### 11.2 编辑保养项目

编辑项目时可调整：

- 名称。
- 启用状态。
- 提醒方式。
- 里程间隔。
- 时间间隔。
- 阈值。
- 排序。

禁用和删除都必须保证该车辆至少还有一个启用项目。

### 11.3 默认模板维护

启动 bootstrap 会保证内置车型和默认保养项目存在。

内置默认项目逻辑：

- `ensureVehicleModels` 按内置 JSON 车型目录补齐内置车型。
- `ensureDefaultMaintenanceItems` 按内置 JSON 模板补齐内置默认保养项目。
- bootstrap 优先按 `catalog_id` 同步内置行；旧数据中没有 `catalog_id` 但品牌、车型、项目名仍匹配的行会被收编。
- 内置 JSON 是内置表的权威来源：新增会插入，变更会更新，移除会删除已带 `catalog_id` 的内置行。
- 这只影响 `vehicle_default_maintenance_items`，不会直接改已经创建车辆的 `maintenance_items`。

## 12. 备份导出和恢复

### 12.1 导出

导出结构：

- `schemaVersion`，当前为 2。
- `cars`。
- `maintenanceItems`。
- `records`。

记录导出：

- 记录日期导出为 `yyyy-MM-dd`。
- 记录项目导出为 `itemIds`。
- 费用导出为 `costCents`。
- 里程导出为 `mileageKm`。

当前备份不导出 `app_preferences`。这意味着当前应用车辆、开发者模式、手动日期、主题模式、通知设置、提醒延后/确认状态和停车倒计时都不随备份迁移。

### 12.2 恢复

恢复入口会先让用户确认，再选择 JSON 文件。

恢复规则：

- 只接受 `schemaVersion=2`。
- 恢复前先校验引用关系。
- 整个恢复在一个数据库事务中执行。
- 事务内先清空当前偏好、车辆、车辆内保养项目、保养记录和记录项目关联。
- 再恢复车辆、车辆内保养项目、保养记录和记录项目关联。
- 恢复不导入内置车型或默认保养模板。
- 恢复时不保留源 ID，会重新生成新 ID。
- 恢复时维护源 car ID 到新 car ID 的映射。
- 恢复时维护源 item ID 到新 item ID 的映射。
- 记录恢复时按映射写入新 car ID 和新 item ID。
- 恢复后当前应用车辆写为第一辆恢复出来的车辆。
- 恢复后手动日期、主题模式、通知设置、提醒延后/确认状态和停车倒计时都保持清空状态，除非后续用户重新设置。
- 如果恢复失败，事务回滚，不留下半导入状态。

引用校验：

- 备份车辆必须有 ID。
- 备份保养项目必须有 ID。
- 保养项目必须引用存在的车辆。
- 保养记录必须引用存在的车辆。
- 保养记录项目必须引用存在的项目。
- 保养记录项目必须属于该记录车辆。

### 12.3 清空数据

清空数据会删除：

- App 偏好。
- 保养记录项目关联。
- 保养记录。
- 车辆内保养项目。
- 车辆。

注意：

- 当前 `_clearAllDataInTransaction` 不删除 `vehicle_models` 和 `vehicle_default_maintenance_items`。
- 恢复备份不会导入默认车型或默认保养模板。
- 修改恢复逻辑时要特别检查备份边界，避免把内置初始化数据重新纳入用户备份。
- 清空后 bootstrap provider 会再次补齐内置车型和默认项目。

## 13. 偏好 key

重要偏好 key：

- `appliedCarId`：当前应用车辆。
- `developerModeEnabled`：开发者模式。
- `manualDateEnabled`：是否启用手动日期。
- `manualDate`：手动日期。
- `themeMode`：主题模式，支持 `light`、`dark`、系统默认。
- `systemNotificationsEnabled`：系统通知是否开启。
- `inAppNotificationsEnabled`：App 内通知是否开启。
- `maintenanceDueEnabled`：保养到期提醒是否开启。
- `maintenanceDueRepeat`：保养到期系统通知重复频率。
- `systemNotificationPermissionRequested`：是否请求过系统通知权限。
- `parkingCountdown`：停车倒计时临时状态，JSON 值，不进入备份。
- `maintenanceReminderSnoozedUntil:{itemId}`：某保养项目延后提醒到期日。
- `maintenanceReminderAcknowledgedOn:{itemId}`：某保养项目当天已确认。
- `mileageUpdateSnoozedUntil:{carId}`：某车辆里程更新延后提醒到期日。
- `mileageUpdateAcknowledgedOn:{carId}`：某车辆里程更新当天已确认。

修改偏好 key 时必须同步检查：

- provider 默认值。
- UI 设置页。
- 通知触发和抑制逻辑。
- 备份恢复是否应保留或清空相关偏好。

## 14. 全局业务约束

日期：

- 所有业务日期按年月日处理。
- 标准格式为 `yyyy-MM-dd`。
- 不在业务逻辑里直接散落读取系统时间，应优先走日期上下文。

里程：

- 车辆当前里程和记录里程均为整数公里。
- 保存记录只允许抬高车辆当前里程。
- 里程提醒中当前里程低于上次保养里程时，已使用里程按 0 处理。

费用：

- 费用以分保存。
- 输入为非负数字。
- 保存时按 `cost * 100` 四舍五入为分。

唯一性：

- 车辆唯一约束为品牌、车型、上路日期。
- 车辆内保养项目名称唯一。
- 同车同日保养记录唯一。
- 同车同日同项目唯一。

数据隔离：

- 保养项目按车辆隔离。
- 保养记录按车辆隔离。
- 提醒、通知和记录列表按当前应用车辆隔离。
- 删除车辆必须清理车辆边界内的数据。
- 停车倒计时不按车辆隔离，是全局临时状态；恢复备份和清空数据会清掉它。

通知：

- 提醒页展示全量启用项目。
- 通知只关心到期和超期项目。
- 当天确认只压制当天。
- 15 天延后包含到期当天，即 `snoozedUntil >= today` 时仍被压制。
- 停车倒计时到点通知和 Android 常驻通知必须一起调度或一起取消。

## 15. 高风险修改点

修改以下逻辑时，应同步补充或检查测试：

- `MaintenanceRules.progressForItem`：影响提醒页、通知候选和状态展示。
- `MaintenanceRules.mileageUpdateFrequencyForRecords`：影响里程更新提醒频率。
- `_buildReminderRows`：影响提醒排序、通知摘要和到期弹窗。
- `_buildScheduledNotifications`：影响系统通知内容和调度。
- `ParkingCountdownRules.progress`：影响停车倒计时卡片状态、颜色和文案。
- `LunioNotificationService.scheduleParkingCountdownNotification`：影响停车倒计时到点提醒和 Android 常驻通知。
- `_showDueInAppNotifications`：影响 App 内弹窗、当天确认和延后提醒。
- `saveMaintenanceRecordWithItemUpdates` / `updateMaintenanceRecordWithItemUpdates`：影响记录保存和提醒间隔回写。
- `restoreBackupPayload`：影响备份恢复事务、ID 重映射和默认数据冲突。
- `effectiveTodayProvider`：影响所有与今天相关的计算。

建议最小验证：

- 提醒和频率：`flutter test test/domain/maintenance_rules_test.dart`。
- 记录、车辆、备份：`flutter test test/data/database_test.dart test/data/backup_codec_test.dart`。
- App 内通知和关键交互：`flutter test test/widget_test.dart`。
- 普通 Dart/Flutter 改动：先跑 `flutter analyze`。
